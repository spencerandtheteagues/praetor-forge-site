Twelve ways agent systems fail — and the control that fixes each.

Most broken automation doesn’t fail because the model is bad. It fails because the operating layer around the model is missing. Select the symptoms you recognise and they are added to your brief.

  1. No acknowledgement, retry queue, or dead-letter path, so customer work quietly disappears.

  2. Agents loop, retry too fast, or use expensive models for cheap work.

  3. Shared keys, no backoff, and too many workers make providers reject useful work.

  4. The health check says the app is running, but no real task is being completed.

  5. A worker dies or stalls and nobody knows until a client complains.

  6. Keys end up in prompts, logs, screenshots, repos, or shell history.

  7. Agents can spend, deploy, delete, or message customers without a human checkpoint.

  8. Sessions expire, tabs drift, and browser tasks fail without a trace.

  9. Retries or parallel workers process the same task twice and create conflicting output.

  10. Backups are missing, stale, or impossible to restore during an incident.

  11. One model is used for everything instead of routing by risk, cost, and difficulty.

  12. No runbook, no smoke test, and no evidence that the owner can operate it.

How we built it

Four hardened layers turning raw frontier models into a deterministic software foundry.

LAYER I · AUTONOMOUS LOOP

Andrej Karpathy’s Keep-or-Revert Loop

Every unit runs a strict transactional cycle: measure baseline → single-hypothesis edit → hard programmatic check → keep or git-revert → institutional attempt ledger so failed ideas never repeat across sittings.

LAYER II · LOOPS & GRAPHS

Typed DAG Execution & Single Human Gate

Complex builds decompose into single-responsibility DAG nodes running across parallel isolated git worktrees with unit-scoped retry — pausing for a single human sign-off strictly at irreversible boundaries.

LAYER III · CLOUDROOM.DEV FABRIC

Fail-Closed Zero-Trust Sandbox Fabric

Built atop open-source Apache-2.0 cloudroom.dev parallel Linux VM sandboxes and hardened with pre-execution SHA-256 exact-bytes manifest verification, host/token isolation, quarantined output pull, and independent local holdout verification.

LAYER IV · FRONTIER COUNCIL

Multi-Provider Sealed Advisor Routing

Routes architecture, implementation, and adversarial review across Claude, Gemini, OpenAI Codex, and Grok inside kernel-sealed advisor sandboxes with strict quota and retry governance.

03RE-ENGINEER · KERNEL-WALLED FORGE

Lawful No-Copy Reverse-Engineering

Lawful no-copy reverse-engineering: enforces an OS kernel wall (sandbox-exec on macOS / bubblewrap on Linux) where only a static study unit (rea-agents Mach-O, plist, and interface analysis) inspects a lawfully held subject to emit a behaviour-only specification, while downstream design, test, and build workers are kernel-blocked from reading the subject and mechanically verified for zero code, text, name, or asset overlap under The Harness Lab brand kit.
